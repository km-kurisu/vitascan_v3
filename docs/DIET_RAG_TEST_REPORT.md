## 1. Architecture & Pipeline

| Stage | What runs | Failure behaviour |
|---|---|---|
1. Knowledge Graph | Curated offline KB (84 Indian foods from IFCT2017/NIN, 20 nutrients, RDA targets, allergies, disorders) builds a deterministic 7-day plan | Always succeeds |
2. Groq LLM (grounded) | `openai/gpt-oss-120b` in JSON mode enriches the plan with culturally flavoured dishes, rationale & bioavailability tips, using only the KB context | Falls back to the KB plan, never crashes |
3. Web augmentation | Live IFCT2017 (`nodef/ifct2017`) cached dataset appends extra nutrient-matched foods when KB coverage is thin | Returns `[]` on any error |
4. Model resolution | Autodetects a usable chat model from the key (env `GROQ_DIET_MODEL` override, else fallback chain) | KB plan used if no model resolves |

## 4. Edge cases & graceful degradation

### 4.1 No safe food exists: B12 + strict vegetarian + dairy allergy

A vegetarian allergic to dairy has **no dietary B12 source** — the system refuses to fabricate one:

```json
{
 "deficiency": "b12",
 "deficiency_label": "B12",
 "target_nutrients": [
  "vitb12"
 ],
 "diet_pref": "vegetarian",
 "allergens": [
  "dairy"
 ],
 "disorders": [],
 "meal_plan": {},
 "bioavailability_tips": [
  "No safe food matched this combination. Please consult a physician/dietitian."
 ],
 "fssai_checked": true,
 "source": "curated_kb+web",
 "coverage": {
  "deficiency": "b12",
  "target_nutrients": [
   "vitb12"
  ],
  "per_nutrient": {
   "vitb12": {
    "available": 0,
    "rda_pct_serving": 0.0
   }
  },
  "adequate": false
 },
 "explanation": [
  "Target nutrient: Vitamin B12 (vitb12), RDA 2.4 ug/day."
 ],
 "web_sources": []
} ...
```

- Coverage reports the nutrient as genuinely unavailable (`available: 0`),
- The plan states *"No safe food matched this combination. Please consult a physician/dietitian."*,
- Live IFCT2017 web sources are still appended so a clinician/nutritionist has raw data.

### 4.2 LLM outage / bad model

When the LLM call fails (network, rate limit, invalid key) the KB plan is returned intact with a `source: curated_kb` flag — verified while the Groq API rejected the default model (`llama-3.3-70b-versatile` was unavailable on this key).

### 4.3 Live rate-limit resilience (proven during this test)

Mid-run, the account exhausted its daily token cap on `openai/gpt-oss-120b` (200k TPD on the free tier). The engine **noted the 429 and automatically retried the same request on the next usable model** (`qwen/qwen3.8-27b`), so runs continued without code changes:

| Condition | Behaviour observed |
|---|---|
| `llama-3.3-70b-versatile` unavailable on key | engine probes `models.list()` and selects the first usable model in `openai/gpt-oss-120b → gpt-oss-20b → groq/compound → qwen → allam` |
| `gpt-oss-120b` daily token cap (429) | per-request retry chain skips to the next model and returns a grounded plan |
| all models saturated | last 429 is swallowed by the caller; the deterministic KB plan is returned unchanged (`source: curated_kb`) |

Chat Q&A behaves identically and falls back to the local grounded answer if every model is saturated.
